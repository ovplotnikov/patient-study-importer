# Производительность версии 2.4.0 — 7 ноября 2026 года

Существенные возможности ускорения есть. Приоритет — запись добровольной диагностики, сохранение Excel при дозагрузке и сверке, повторные чтения базы и создание элементов интерфейса. Два существующих OCR-движка можно выполнять одновременно: на проверенном наборе это уменьшило время на 10–28% при полностью совпадающем результате. Менять модель, снижать разрешение или отменять ручную проверку для этого не требуется.

Это аудит с измерительными прототипами. Код приложения, основная ветка и опубликованный выпуск не менялись.

## Как проверяли

- Продукт: 2.4.0, коммит `f17e5f46f32c9dbaa7aae98fb40e5f6c19c4ed7d`. Стенд: `050c706b75341acc121fc7c9e4fd787a79f51134`.
- [Успешный Windows-прогон](https://github.com/ovplotnikov/patient-study-importer/actions/runs/42390490455): Windows Server 2022 x64, Python 3.12.10, AMD EPYC 7763, выделено 2 ядра / 4 логических процессора, около 16 ГБ RAM. Зависимости и проверенные SHA-256 весов совпадают с релизом. Tesseract 5.5.3.20260724.
- Только автоматически созданные вымышленные документы и временные рабочие папки. Отчёты пользователей и реальные исследования не использовались. Сеть нужна для установки зависимостей и загрузки официального выпуска/весов, не для обработки документов.
- Сценарии идут последовательно. Основные сравнения Excel и чтения базы повторены трижды, разбор — семь раз, OCR — два прогретых прохода каждого сценария и один первый проход в новом процессе каждого режима. Порядок вариантов Excel и разбора чередуется.
- [Исходные измерения](../benchmarks/performance/results/windows-2026-11-07/) и [скрипты](../benchmarks/performance/README.md) сохранены. Локальные предварительные замеры на занятом Mac не использованы для таблиц ниже; отдельная проверка границы согласия на Mac отмечена явно.

Числа относятся к этому стенду, а не к любому компьютеру врача. Большие синтетические базы показывают масштабирование; они не доказывают частоту таких сценариев у пользователей. Совпадение результатов на тестовом наборе не заменяет регрессионные проверки будущей реализации.

## Добровольная диагностика: устранить запись на диск для каждого счётчика

Это [отдельный успешный Windows-прогон](https://github.com/ovplotnikov/patient-study-importer/actions/runs/42391558144) на коммите `05b0fba35d9c8be7398e863ced8b073667be7dd5`, Windows Server 2022, Python 3.12.10. CPU второго runner отдельно не зафиксирован. Три повтора; только временные состояния согласия и вымышленные `formats/pdf`, `outcomes/saved`. Сетевой транспорт заблокирован, запросов ноль.

| Вымышленных файлов | Текущая запись с согласием | Те же суммы группой | Диагностика выключена |
| --- | ---: | ---: | ---: |
| 100 | 1,940 с | 0,066 с | 0,046 с |
| 1000 | 19,079 с | 0,477 с | 0,456 с |

Это время чтения согласия и записи двух счётчиков на файл, а не полного импорта. Другие причины проверки и отправка по сети не измерялись. Не следует складывать эти числа с результатами другого runner и выдавать сумму за замер приложения.

Сейчас `_diagnostic_batch()` вызывает `record()` дважды для каждой попытки, начатой при включённой диагностике. Каждый вызов читает состояние, создаёт временный файл, делает `fsync` и атомарную замену. На 1000 файлов получается 2000 записей. Уже существующий аргумент `count` позволил сохранить идентичные суммы двумя записями: состояние совпало побайтово, снимок отчёта тоже совпал. Все 1000 проверок согласия в прототипе оставлены. Выключенная диагностика ничего не записывает.

Для продукта нужен один атомарный `record_batch`, который объединяет счётчики в памяти, строго проверяет прежнюю схему, пределы значений и актуальное согласие под блокировкой. Нельзя просто убрать `fsync`: достаточно вызывать его один раз на весь небольшой набор. Выигрыш в таблице доказывает стоимость I/O, но не готовность такого API.

Дополнительно на Mac воспроизведён крайний случай версии 2.4.0: попытка импорта запоминает `collect=True`; пользователь выключает диагностику и снова включает её до конца пачки; при завершении прежние счётчики этой попытки возвращаются в очередь. Это технические суммы без персональных данных, отправки в проверке не было. Для группового сохранения нужно привязать попытки к локальному `epoch` согласия и отбрасывать старые группы даже после повторного согласия. Существующую защиту параллельной отправки и проверки подтверждения следует сохранить. [Результат воспроизведения](../benchmarks/performance/results/windows-2026-11-07/consent-edge-macos.json).

## Excel: измеренное ускорение без изменения книги

Сценарий: к уже заполненной базе добавляются одно новое исследование и две копии — побайтовая и с отличающимся пробелом. На документ приходится 10 показателей, на пациента — пять исследований. В книге заранее есть пользовательская заметка, формула в дополнительной колонке и собственный лист.

| Документов до добавления | Текущий код, медиана | Прототип, медиана | Сокращение времени |
| --- | ---: | ---: | ---: |
| 100 | 1,55 с | 1,27 с | 18% |
| 1000 | 16,19 с | 12,56 с | 22% |

Прототип объединяет три изменения:

1. Индекс `arrivals(document_id)` вместо повторных полных просмотров таблицы поступлений.
2. Один каталог сохранённых оригиналов на экспорт вместо `glob` по всей папке для каждого поступления. На 1000 исследованиях в комбинированном прототипе число вызовов `os.scandir` падает с 1008 до 5, подготовка строк — с 1,74 до 0,32 с.
3. Повторное использование одинаковых `Font`, `Alignment`, `PatternFill` вместо нового объекта на каждой ячейке. В комбинированном прототипе заполнение и оформление листов — с 7,27 до 5,14 с.

Загрузка существующего XLSX (около 3,45 с) и его сохранение (около 3,05 с) остаются. Пик памяти процесса почти не меняется: около 287 MiB. Создание индекса выполняется до измеряемой операции; это разовая стоимость будущей миграции. Время вложенных этапов нельзя складывать с временем содержащей их операции.

Отдельные однократные измерения на 1000 документах дали 16,09 с для текущего кода, 15,93 с с одним индексом, 14,84 с с каталогом, 15,25 с с кешированием стилей. Они показывают направление, но не служат точной оценкой независимого вклада: для этого нужны повторные сравнения.

После каждого опыта проверены хэши всех ZIP-частей XLSX, включая стили, формулы и связи; исключён целиком файл служебных свойств `docProps/core.xml`, в котором обновляется время сохранения. Хэши совпали между вариантами. Отдельно проверены заметка, собственная колонка, лист, два вида дублей, `quick_check` и внешние ключи SQLite.

Одиночные контрольные импорты показывают другую картину для большой новой пачки: 500 небольших TXT заняли 20,51 с, из них 9,29 с — перенос файлов; 500 точных копий — 16,62 с, из них перенос 9,69 с. Здесь существенны операции с файлами, а вывод о доминировании Excel относится прежде всего к дозагрузке и ручной сверке накопленной базы. Проверки целостности, долговечность записей и возможность восстановления после сбоя сохраняются.

### Что даёт больший выигрыш при ручной сверке

Сейчас каждое подтверждение пациента или данных сохраняет всю книгу, делает резервные копии и выполняет эту работу в потоке Tk. Поэтому даже ускоренный экспорт большой книги всё равно будет останавливать интерфейс на секунды.

Первый шаг — выполнить ту же последовательность операций в рабочем потоке, сохранив блокировку, проверку ревизии, недоступность повторного подтверждения и обработку ошибок. Это повысит отзывчивость, но само по себе не сократит время записи.

Следующий шаг — сохранять решения в базе и объединять обновления Excel, показывая состояние несохранённой таблицы и запрещая открывать устаревший результат. Это более серьёзное изменение: нужны проверки аварийного завершения, закрытия окна, занятого Excel, повторного запуска и пользовательских правок. Его выигрыш в этом аудите не измерялся.

## Интерфейс: повторная работа становится заметной при росте базы

В сценарии чтения на исследование приходится 30 показателей и 63 строки OCR со свидетельствами, 10% требуют проверки. На 5000 документов база занимает около 271 МБ.

| Операция | 100 документов | 1000 документов | 5000 документов |
| --- | ---: | ---: | ---: |
| Один `summary()` | 0,043 с | 0,488 с | 2,952 с |
| Два `summary()` подряд, как при обновлении списка | 0,084 с | 0,945 с | 5,813 с |
| Полная загрузка очереди проверки | 0,046 с | 0,496 с | 2,400 с |
| Статусы последней пачки: отдельный запрос на файл | 0,155 с / 100 файлов | 0,770 с / 500 файлов | 0,784 с / 500 файлов |
| Те же статусы одним групповым чтением | 0,033 с / 100 файлов | 0,160 с / 500 файлов | 0,160 с / 500 файлов |

`summary()` читает все документы и разбирает JSON. Главный экран вызывает его дважды; экран результатов дополнительно загружает полную очередь проверки ради одного признака. Первые изменения: одна согласованная сводка на обновление экрана, только нужные поля SQL, групповое получение статусов. Затем возможен кеш показателей исследований по ревизии; счётчики поступлений, ошибок и незавершённых перемещений меняются независимо, их и состояние экспорта/файла Excel нужно читать отдельно.

Настоящий Tk на Windows тоже проверен. Повторное заполнение неизменившейся очереди занимает 35 мс для 10 файлов, 315 мс для 100 и 3,285 с для 1000. Первый показ 1000 файлов — 3,013 с. Создаются заново все строки и дочерние виджеты; это происходит и при возврате фокуса. Измерены callback и `update_idletasks` в скрытом окне, без видимой перерисовки. Нужны обновление только изменённых строк и ограниченный видимый список. Ускорение этих изменений пока не измерялось.

## OCR: сохраняем оба движка и контроль качества

Сравнивались существующие RapidOCR/PaddleOCR Cyrillic и Tesseract с теми же весами, пикселями, разрешением и дополнительными проходами ориентации. Прототип выполняет один вызов Rapid и один Tesseract одновременно на одной странице; страницы между собой не распараллеливаются.

| Синтетический случай | Последовательно | Одновременно | Сокращение времени |
| --- | ---: | ---: | ---: |
| Чистый бланк | 1,193 с | 0,946 с | 21% |
| Поворот на 90° | 3,202 с | 2,870 с | 10% |
| Мелкий шрифт | 1,277 с | 1,000 с | 22% |
| Наклон | 1,394 с | 1,151 с | 17% |
| Страница сканированного PDF | 2,040 с | 1,471 с | 28% |

Первое распознавание в новом процессе: 2,588 → 1,960 с. Полностью совпали результаты `Page`, координаты, уверенность, альтернативы, извлечённые данные, разбор и контроль качества. Обязательная ручная сверка сканов сохраняется. Пик Python-процесса: 746 → 761 MiB; память отдельного Tesseract на Windows здесь не измерена, это не общий максимум всей программы.

Передача PNG через stdin вместо временного файла дала смешанный небольшой дополнительный эффект: в сумме пяти медиан около 1% против одного распараллеливания, PDF стал немного медленнее. Приоритет низкий, двух повторов недостаточно для вывода о стабильном выигрыше.

Для шести одинаковых встроенных изображений в одном PDF кеш распознавания дал 7,64 → 1,29 с при идентичном результате. Это узкий сценарий повторных вложений, а не шестикратное ускорение любых PDF. Продуктовый кеш должен иметь ограничение памяти, жить только в рамках одного чтения PDF, не кешировать неудачи и сохранять привязку свидетельств к страницам. Повторное распознавание по явной команде должно оставаться новым чтением.

Общий экземпляр RapidOCR не следует одновременно использовать для разных страниц: библиотека меняет состояние вызова. Не нужно увеличивать число потоков вслепую: [ONNX Runtime описывает конкуренцию пулов и зависимость эффекта от модели](https://onnxruntime.ai/docs/performance/tune-performance/threading.html). Текущие два intra-op потока сохранены.

## Разбор: убрать повторные вычисления

| Сценарий | Сейчас | Прототип | Ограничение результата |
| --- | ---: | ---: | --- |
| 20 лабораторных строк на странице | 5,15 мс | 2,16 мс | Небольшой абсолютный выигрыш |
| 100 строк | 66,97 мс | 7,52 мс | Дата страницы вычисляется один раз |
| 500 строк | 1,440 с | 0,032 с | Большой синтетический текст, не обычная бумажная страница |
| Кандидаты пациентов: 1000 пациентов, 10% неоднозначных документов | 39,49 мс | 3,52 мс | Только этап сопоставления |
| 3000 пациентов, 10% неоднозначных | 490,49 мс | 12,79 мс | Только этап сопоставления |

Первый прототип кеширует дату по номеру страницы, второй заменяет повторные сортировку/сканирование всех пациентов индексами по ФИО и дате рождения. Правила совпадения, порядок кандидатов и весь результат сохранены. Проверены также разные и отсутствующие даты на нескольких страницах. Большие коэффициенты здесь нельзя переносить на полное время импорта или OCR.

## Запуск и размер EXE

Проверен именно опубликованный EXE 2.4.0. До маркера после импорта GUI и создания скрытого Tk: первый запуск 5,52 с, медиана пяти запусков 4,62 с. Это не время до готовности рабочего экрана. Кеш ОС не сбрасывался.

Тот же probe из исходников при уже установленном Python: медиана 0,377 с. Разница указывает на значимую стоимость упаковки/запуска, но не доказывает время будущей оптимизированной сборки. [PyInstaller распаковывает поддерживающие файлы onefile при каждом запуске](https://pyinstaller.org/en/stable/operating-mode.html#how-the-one-file-program-works).

В EXE размером 191,97 МБ обнаружены 53 пары одинаковых DLL Tesseract в корне и `vendor/tesseract`; совпадение подтверждено SHA-256. Одна лишняя копия занимает 35,13 МБ в EXE и 92,49 МБ после распаковки. Общий объём извлекаемых бинарных/вспомогательных записей — 453,96 МБ. Это резерв уменьшения размера примерно на 18%, а не обещание такого же ускорения запуска. Перед удалением нужно проверить пути загрузки DLL, OCR, переносимость и автообновление на чистой Windows.

Переход к папке установленной программы с отдельными моделями может уменьшить повторную распаковку сильнее. Пользователю по-прежнему не нужен Python, но текущий обновлятор заменяет только EXE: такая смена упаковки потребует отдельного протокола обновления и отката. Для первого небольшого выпуска это не приоритет.

## Дополнительные находки по исходникам

- Предпросмотр заново рендерит ту же PDF-страницу при выборе показателя. Стоит отделить рамку выделения от отрисованной страницы и ограничить кеш по памяти.
- Многостраничный TIFF сразу декодируется целиком в RGB. Лучше загружать текущий кадр и небольшой соседний кеш. Потенциальный выигрыш здесь не измерен.
- PDFium нельзя просто вызывать из нескольких потоков одновременно, даже для разных документов: нужен общий последовательный доступ или отдельный процесс. [Ограничение pypdfium2](https://pypdfium2.readthedocs.io/en/stable/python_api.html#incompatibility-with-threading).

## Порядок дальнейшей работы

1. Групповая запись диагностики с защитой актуального согласия. Затем небольшие изменения с проверяемой эквивалентностью: каталог оригиналов, повторное использование стилей, индекс поступлений, кеш даты страницы, групповые SQL-чтения и устранение двойной сводки.
2. Отзывчивость: фоновое сохранение после сверки, обновление только изменённых строк, ограниченный предпросмотр. Отдельно проверить отмену, закрытие и повторные нажатия.
3. Параллельные два OCR-движка на одной странице с ограничением памяти, прежними fallback и обязательной ручной проверкой; сравнить также на слабом Windows-компьютере.
4. Уменьшение дистрибутива; изменение всего формата установки — отдельная задача.

Не отключать второй OCR-движок, не уменьшать разрешение, не снимать ручную сверку, `fsync`, `synchronous=FULL`, проверки хэшей или резервное копирование ради скорости. Для небольших папок текущая архитектура приемлема: например, 10 текстовых бланков импортировались за 0,62 с. Главный риск роста — повторное сохранение и синхронное чтение накопленной базы.
