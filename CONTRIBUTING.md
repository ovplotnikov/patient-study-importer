# Как помочь проекту

Описание, инструкции и обсуждение функциональности ведём по-русски. Можно предлагать исправления и поддержку новых бланков. Репозиторий открыт для форков и PR.

## Данные для разработки

Прочитайте [правила обращения с данными](docs/PRIVACY.md). Только созданные с нуля вымышленные примеры. Реальные документы, даже с закрашенным ФИО, в Issues, PR, коммиты, тестовые артефакты и журналы не принимаются. Все локальные клинические данные храните вне checkout. `.gitignore` предотвращает часть случайных добавлений, но не гарантирует отсутствие ПД в текстовых файлах.

Для нового шаблона полезен пустой бланк без персональных сведений или вымышленный пример с тем же расположением полей. Пример должен воспроизводить структуру и ошибку разбора. К письмам и Issues применяются те же правила.

## Устройство программы

- `patient_importer/extraction.py` — чтение файлов и локальное OCR.
- `patient_importer/parsing.py` — заголовки пациента, даты, лабораторные строки и классификация исследований.
- `patient_importer/analysis.py` — измерения из описаний, контекст, сопоставление пациентов.
- `patient_importer/storage.py` — база, повторы, перемещение файлов, резервные копии.
- `patient_importer/workbook.py` — Excel и сохранение пользовательских записей.
- `patient_importer/gui.py` — интерфейс.
- `tests/test_engine.py`, `patient_importer/smoke.py` — вымышленные примеры и проверки.

Отдельной системы подключаемых парсеров клиник пока нет. Изменения в общих правилах могут повлиять на другие формы.

## Добавить шаблон

1. Опишите тип исследования, формат, структуру заголовков и колонок. Название клиники допустимо, но не заменяет описание конкретной версии бланка.
2. Создайте синтетический пример с сохранением структуры, но с полностью придуманным содержимым. Предпочтительно генерируйте PDF/DOCX/изображение в тесте, а не добавляйте бинарный файл.
3. Задайте ожидаемые поля: ФИО, дата рождения, дата исследования, название показателя, значение, единица, референс, сторона и исходный фрагмент. Не объявляйте успех только по числу строк.
4. Добавьте положительный тест и отрицательные случаи: похожий бланк с другим порядком колонок, отсутствующая дата, подпись врача вместо пациента, неоднозначные единицы, несколько пациентов. При изменении общих правил проверьте прежние формы.
5. Реализуйте минимальное правило с явными признаками шаблона. Не подставляйте недостающие значения и не объединяйте пациентов по похожим именам или папке.
6. Если нужен отдельный обработчик, вынесите его в модуль и явно подключите в существующий разбор. Регистрация плагинов автоматически сейчас не выполняется.
7. Обновите [таблицу совместимости](docs/SUPPORTED_FORMS.md): что проверено тестами и что требует ручной сверки. Не заявляйте поддержку всей клиники по одному бланку.

## Проверки и PR

Python 3.12, зависимости из `requirements.txt`, команда `python -m unittest discover -s tests -v`. Windows CI дополнительно запускает упакованную программу и OCR на синтетических документах. Скриншоты CI также должны содержать только тестовые данные.

Перед коммитом прочитайте staged diff и проверьте все добавляемые файлы. В PR укажите поведение до/после, ожидаемые поля, тесты и ограничения. Не выводите текст реальных документов в сообщения об ошибках или отчёт CI.

Диагностика принимает только счётчики по заранее заданным техническим кодам. Изменения формата, списка кодов и правил хранения проверяйте в приложении и на приёмнике. Содержимое документов и сообщения исключений остаются вне схемы. [Контракт добровольной диагностики](docs/TELEMETRY.md).

## Выпуски

Проверки PR имеют только read-доступ; сборка из PR не публикует релиз. После проверки владелец объединяет изменения, меняет номер версии в `patient_importer/__init__.py` и создаёт соответствующий тег `vX.Y.Z`. Тег запускает тесты, сборку и публикацию ZIP. Не перезаписывайте теги уже вышедших версий ради изменения поведения программы.

Изменение схемы базы требует описания миграции, резервного копирования и совместимости. Смена правил разбора сама по себе не означает автоматический повторный разбор уже импортированных файлов: повторы могут быть пропущены. Не обещайте перерасчёт существующей базы без отдельного механизма и теста.

Код проекта — MIT; лицензии зависимостей сохраняются отдельно. Отправляя код, убедитесь, что вправе предоставить его на условиях проекта и что он не содержит данных пациентов.

## Протокол обновления

`packaging/package_release.py` создаёт `update.json` с версией, SHA-256 EXE и идентификатором формата данных. `patient_importer/updater.py` проверяет стабильный выпуск официального репозитория, checksum ZIP и EXE, совместимость, затем запускает отдельную копию текущего EXE как установщик. Обновляются только EXE и `installation.json`; оригиналы и база не входят в операцию.

При несовместимом изменении схемы нужно изменить `DATA_FORMAT` и описать отдельную миграцию; не оставляйте прежний маркер совместимости. Сохраните служебный режим `--update-probe`: предыдущая версия использует его для проверки кандидата перед заменой. Windows CI проверяет ожидание закрытия занятого EXE, замену, резервную копию, перезапуск и неизменность синтетических данных.
